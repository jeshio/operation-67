# Передача серверному мастеру

Этот этап изменяет только репозиторий. SSH, VPS, публичное приложение, firewall, systemd, GitHub settings, commit/push/merge и deployment не выполнялись. Прочитайте APP_CONTRACT.md и RELEASE_POLICY.md; не переносите прежние IP/домены/права из исторических скриптов без проверки.

## Перед первым релизом

- Аудит VPS: ОС и обновления, Node 24, архитектура (текущий GitHub runner создаёт linux-x64; для arm64 нужен отдельный проверенный Linux build), диски/лимиты, служебные пользователи, systemd unit, реальные env, доступность 5179 только локально, firewall, reverse proxy, WebSocket, STUN/relay.
- Проверка признаков взлома и сохранение доказательств до изменений при подозрении. Сертификаты, журналы, log rotation, retention и серверные резервные копии — ваша ответственность. Не переносить приватные ключи или журналы в репозиторий/CI artifacts.
- Создать ограниченного deployment-пользователя: загрузка во staging, вызов только фиксированного root-owned wrapper. Не выдавать shell/root/Docker socket или возможность менять helper/unit/scripts. Проверить все аргументы и пути, происхождение artifact и SHA, права staging против подмены между проверкой и распаковкой.
- Первый переход с legacy версии выполнить отдельно: прежний runtime не знает release identity/drain. Новый архив не содержит старого установщика/Caddy/systemd-файлов. Сохранить старую установку для ручного аварийного восстановления; не объявлять её автоматически проверенным rollback target.
- Сопоставить ALLOWED_ORIGINS и точные TRUSTED_PROXY_IPS с реальной топологией, проверить spoofed X-Forwarded-For и четыре устройства за одним NAT. Добавить HSTS на HTTPS-прокси после проверки сертификата, ограничить тела/соединения/скорость там же.

## Workflows, которые ещё требуется установить

1. Deploy по выбранному успешному CI artifact/commit, через защищённое production environment с approval, минимальными permissions и короткоживущим/ограниченным доступом. Проверять SHA-256 до распаковки, не собирать на VPS.
2. Production verification: точный SHA, `/health`, `/ready`, HTTPS, статические ресурсы и безопасные негативные проверки. Отчёт без секретов и адресов игроков.
3. Rollback на предыдущий сохранённый проверенный artifact, проверка ожидаемого SHA и service overrides после возврата. Комнаты потеряются; автоматические разрушительные операции с данными запрещены.
4. Maintenance: локальный SIGUSR2, наблюдение `/health.rooms`, конечный срок ожидания и понятная отмена SIGHUP; не создавать публичный admin endpoint. Доступ к сигналам только для штатного main PID.
5. Политика хранения: несколько предыдущих артефактов/manifest/SHA и журнал решений; GitHub retention 30 дней недостаточен как единственная резервная копия.

Проверить весь путь на тестовой установке: плохая SHA/архив/версия отклоняются, активные комнаты не перезапускаются, запуск и откат ограничены по времени, ошибка публичной проверки вызывает проверяемый возврат, ошибка самого rollback остаётся заметной. Локальные container mocks не подтверждают правильность реального systemd/VPS.
