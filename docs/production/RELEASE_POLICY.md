# Политика выпуска

1. Изменения проходят PR, `CI / verify`, review diff и dependency/security отчётов. Нет auto-merge, автоматического major upgrade и blanket-ignore. High/critical и ошибка scanner блокируют выпуск; применимость remaining low/moderate письменно разбирается владельцем.
2. Linux CI на чистом checkout выполняет `pnpm verify`, dependency audit, Gitleaks всей истории и рабочего snapshot, actionlint, локальные Semgrep rules, browser test, упаковку и запуск распакованного runtime, изолированный тест release.sh. Build содержит полный SHA; dirty build не выпускается.
3. CI сохраняет `linux-runtime-<commit>` с архивом и SHA-256 на 30 дней. Это подготовка артефакта, не deployment. Серверный мастер должен настроить более длительное хранение предыдущих проверенных артефактов и защищённый release workflow.
4. До распаковки доверенный `scripts/security/archive.py` проверяет ожидаемую SHA-256, все пути, типы, размеры, дубликаты, symlink и отсутствие записи через symlink-parent. Проверенная последовательность байтов фиксируется в памяти (архив максимум 128 МиБ), поэтому последующая запись загрузчиком в исходный файл не подменяет распаковываемые данные. Распакованный объём ограничен 512 МиБ и 50 000 записей. Затем проверяются состав, manifest и контрольные суммы. Валидатор работает в изолированном режиме Python и не использует отключаемые assert для защиты. Hard links, устройства и внешние ссылки запрещены. Приложение не импортируется от root.
5. `release.sh deploy ARCHIVE EXPECTED_SHA256 [MAX_ROOMS]` требует явный `PUBLIC_ORIGIN=https://...`, Node 24, Python 3.11+, управляемую установку, lock и доверенный helper вне загруженного архива. SHA берётся из успешного доверенного CI, а не только из присланного рядом файла. Лимит комнат 1–64.
6. Скрипт подтверждает поддержку drain, запрещает входы сигналом SIGUSR2, требует rooms=0 и сохраняет предыдущий полный комплект и override лимита. Если комнаты заняты, отменяет drain и прекращает обновление. Продолжительное ожидание освобождения комнат организует будущий maintenance workflow.
7. После замены проверяются локальные health/readiness и публичный readiness с точным ожидаемым SHA и dirty=false. При ошибке возвращаются файлы и override, и проверяется SHA предыдущей версии. Неуспешный rollback требует вмешательства оператора; исходная ошибка всегда остаётся ненулевым выходом.
8. `release.sh rollback BACKUP` использует только проверенную копию под `backups/`. Данные игры в памяти не восстанавливаются. Разрушительный автоматический откат данных запрещён; БД сейчас отсутствует.

Первый переход со старой установки не поддерживает этот автоматический сценарий: отсутствуют manifest/drain. Его после аудита VPS делает второй мастер с отдельным проверяемым планом. Исторический `install.sh` и старые команды распаковки не являются безопасным новым release-путём и не входят в архив. Доверенные operator scripts должны быть root-owned и недоступны для изменения deployment/app-пользователем.

Docker — альтернатива с закреплёнными Node/Caddy digest, непривилегированным app USER, read-only rootfs и ограничениями compose. Перед build передать полный `RELEASE_COMMIT`; `RELEASE_DIRTY=false` допустим только для подтверждённого чистого checkout. Эта декларация в Docker не заменяет контроль CI. Не запускать compose с примером нулевого SHA или неизвестной чистотой как production.

Все действующие серверные команды, sudoers, approval environment, rollback/verification/maintenance workflows и управление сертификатами устанавливает второй мастер. Ни один workflow нельзя считать работающим до реального запуска в GitHub и проверки нужных прав.
