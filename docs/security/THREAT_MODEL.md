# Модель угроз

## Система и данные

Клиент TypeScript/Three.js работает в браузере; Node/Colyseus координирует комнаты и выдаёт гостевые резервации. Бой считает выбранный игрок-хост в WebWorker. Участники обмениваются данными через WebRTC; резервный маршрут — WebSocket через сервер. В этой реализации нет БД, учётных записей, платежей и загрузки пользовательских файлов. Комнаты и гостевые ключи находятся в памяти; рекорды, имя и настройки — в localStorage браузера.

Доверенные границы: HTTPS reverse proxy → HTTP/WebSocket сервер → комната → участник и текущий host/epoch/round. Отдельно: reviewed source/lockfile → CI → неизменяемый артефакт → deployment-пользователь → systemd. Данные внутри архива не являются доверенными инструкциями.

## Противник и меры

| Угроза | Мера | Остаточное ограничение |
|---|---|---|
| Вход в личную комнату через стандартный Colyseus API | Все внешние `/matchmake*` закрыты; `setPrivate`; выдача резерваций только `/api/join` | Приглашение — шестизначный hex-код, его можно передать другому человеку |
| Подмена гостя или вкладки | Случайный 192-битный bearer token, проверка регистрации, штатная замена сессии | Украденный token даёт права гостя; аккаунта и механизма восстановления нет |
| Некорректные WebRTC сообщения | Проверки формы, типов, UTF-8 размера, отправителя и адресата до вызова плагина | SDP не считается доверенным игровым состоянием |
| Подмена host/snapshot/input | Проверки комнаты, отправителя, host authority и battle context в relay/coordinator/client | Сам легальный host может мошенничать |
| Подбор кода/заполнение комнат | Лимиты IP и процесса, ограниченные таблицы, 64 заявки в очереди, 5-секундный deadline | Распределённый DDoS требует защиты reverse proxy/провайдера |
| Cross-origin браузерный доступ | Единая точная allowlist HTTP и WebSocket; production требует HTTPS origins | Native-клиент может подделать/не прислать Origin; это не аутентификация |
| XSS/встраивание/утечка файлов | CSP, nosniff, no-referrer, frame-ancestors none; реальный путь, список MIME, запрет dotfiles и QA | Inline styles нужны интерфейсу; source/зависимости всё равно требуют review |
| Уязвимые зависимости/Actions/секреты | Frozen lock, review графа, audit, закреплённые actions и инструменты, Gitleaks, Semgrep, watcher | Автоматические проверки не доказывают отсутствие неизвестных уязвимостей |
| Опасный архив/неверный релиз | SHA-256 из доверенного CI, проверка путей/ссылок/manifest до распаковки, release identity и проверяемый rollback | Получение доверенного SHA и права deployment настраивает серверный мастер |

## Осознанно сохранённые ограничения

1. Легальный игрок-хост может подделать счёт, ход боя и результаты. Это развлекательная игра без серверно подтверждённых наград. Для соревновательных/денежных сценариев нужна другая архитектура.
2. Прямой WebRTC раскрывает сетевые адреса участникам. STUN видит сетевой адрес запроса. TURN-only режим не добавлен.
3. Перезапуск теряет комнаты и гостевые ключи. Browser storage можно изменить пользователем; это не защищённый журнал результатов.
4. Публичные `/health`, `/ready`, список общих комнат раскрывают только безопасное состояние и commit SHA, без токенов, IP, окружения, стеков и служебной QA-диагностики.
5. Лимиты разделяются игроками за NAT; стандартный сценарий четырёх игроков проверяется. В большой общей сети потребуется согласованная настройка на прокси.
6. VPS, сертификаты, firewall, реальные логи и работающая версия в этом этапе не проверялись. Признаков взлома по изученному репозиторию не установлено; это не заключение о сервере.
