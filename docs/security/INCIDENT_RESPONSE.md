# Подозрение на компрометацию

Признаки: неожиданные процессы/ключи/пользователи, изменение runtime вне CI, утечка токена, необъяснимые исходящие соединения, выполнение кода через уязвимость в период публичной экспозиции, изменение workflow/permissions. Наличие advisory само по себе не доказывает взлом.

1. Остановить обычные релизы и auto-операции. Зафиксировать время, commit/artifact SHA, наблюдения и доступы. Не очищать логи и не переписывать историю до сохранения evidence. Не включать секреты/IP игроков в публичные Issues или CI artifacts.
2. Владелец и серверный мастер изолируют затронутую систему и ограничивают входы в рамках отдельного разрешённого серверного плана. Снять snapshot/копии необходимых журналов с ограниченным доступом, записать checksum и цепочку действий. Данный агент не подключается к VPS самостоятельно.
3. Определить область: приложение, Node/ОС, proxy, GitHub Actions, deployment credentials, личные устройства. Если сервер/root скомпрометирован, не считать замену app-архива достаточным восстановлением.
4. Отозвать/перевыпустить затронутые credentials через владельца, проверить active sessions и доступы, удалить persistence после сохранения evidence. В игре нет постоянных аккаунтов; рестарт сбрасывает гостевые tokens, но не заменяет анализ источника компрометации.
5. Восстановить из доверенного source/clean environment и проверенного artifact; при необходимости пересоздать хост. Проверить ограничения пользователей, secrets, policy, health/readiness/SHA и внешние признаки проблемы.
6. Документировать первопричину, исправление и проверки, уведомить затронутых лиц при подтверждённой утечке и применимых обязательствах с владельцем. Закрытие security Issue и обычный deploy не закрывают incident автоматически.

Ни автоматического разрушительного rollback данных, ни удаления логов, ни «лечения» неизвестного сервера этим набором workflows не предусмотрено.
