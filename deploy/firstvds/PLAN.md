## Переход с legacy runtime

Старый /health: protocol 5, maxRooms 64, rooms 0; /ready отсутствует.
Не посылать ему SIGUSR2. Сохранить закрытый архив старой установки, конфигураций
служб и HTTPS для ручного восстановления вне источника. Не объявлять его
автоматически проверенным rollback target новой схемы.

1. Проверить чистый Linux runtime через CI: verify, dependencies, Actions
   advisories, Gitleaks, actionlint, Semgrep, browser, archive и release fixtures.
2. Использовать проверенный CI archive и SHA256. Доверенный archive.py находится
   вне загружаемого комплекта; проверяет байты, пути, manifests и архитектуру.
   Runtime никогда не исполняется от root. На VPS приложение не компилируется:
   из готового runtime собирается только контейнерный слой COPY без RUN.
3. Создать отдельный operation67-edge, subnet 172.31.67.0/28 после проверки
   конфликтов. Только игра (.3) и общий Caddy (.2). У игры нет host ports,
   state volumes, Docker socket или доступа к соседним проектам.
4. Caddy: добавить проектную конфигурацию и сеть в постоянный Compose,
   подключить сеть к работающему контейнеру без пересоздания, validate/reload.
   Сохранить приватное TLS-состояние вне VPS до/после изменения.
5. До DNS проверить новый runtime через SSH tunnel: точный SHA, readiness,
   assets, закрытые маршруты, origin и WebSocket. GAME_QA не включать.
6. Переключить только A-запись 67.jeshio.ru. Получить сертификат, проверить
   публичные HTTPS/WSS, обычный UI и четыре клиента за одним NAT.
7. При пустых старых комнатах перевести старый HTTPS в проверяемый прокси
   нового HTTPS, чтобы старый DNS не создавал вторую группу комнат. Затем
   остановить/отключить старый игровой процесс. Legacy IP перенаправлять на домен.
8. Сохранить артефакт, образ и инфраструктурные конфиги вне старого VPS,
   проверить рестарт контейнера и возврат на сохранённый проверенный image ID.
   Не удалять исходную установку или старый VPS.

Лимит 64 комнаты сохранён, RAM 512 MiB, CPU 1. Короткая функциональная проверка
не подтверждает вместимость нового VPS. Рекорды и настройки остаются в браузерах;
игровые комнаты существуют только в памяти процесса.

Автодеплой и новые SSH/CI credentials в это поручение не входят. Первый перенос
выполняется оператором с существующим административным доступом. Владелец
19.10.2026 отдельно разрешил commit/push, создание PR и merge после успешного CI
для этого переноса.

верхнего уровня. Security gates не ослабляются. Владелец 19.10.2026 установил
общее правило для всех проектов на FirstVDS: low/moderate не блокируют выпуск,
находки остаются в отчётах. Разбор применимости выше сохранён; high/critical и
ошибки scanner блокируют выпуск. Отдельно применяется уже подготовленный
в исходном рабочем дереве фикс UID/GID Semgrep: isolation остаётся прежней,
0700 snapshot доступен его владельцу, root capabilities не добавляются.
