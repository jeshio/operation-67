## Подготовка артефакта

На Linux с Node 24.21.0 и pnpm 10.33.2, в чистом checkout:

```sh
pnpm install --frozen-lockfile --ignore-scripts
pnpm rebuild esbuild
pnpm verify
pnpm security:dependencies
node scripts/security/install-tools.mjs
pnpm security:tools
pnpm package:vps
node scripts/security/test-archive.mjs
```

Архив `test-artifacts/roma67-vps.tar.gz` и `.sha256` содержит только runtime. Для локальной проверки на Mac разрешён `--allow-dirty` у package:vps и `--allow-local` у test-archive; production release.sh эти флаги не использует. Для CI дополнительно обязательны browser test и одноразовый container test из TESTING.md.

## Выпуск и возврат — после настройки вторым мастером

Доверенные release.sh и scripts/security/archive.py устанавливаются вместе, вне загруженного архива, root-owned. Helper нужен Python 3.11+. Скрипт требует управляемую установку с release/integrity manifests, поддержку drain, Node 24, ожидаемый SHA-256 из доверенного CI и явный PUBLIC_ORIGIN. Нельзя просто загрузить присланный архив и выполнить скрипт из него от root.

Интерфейс: `release.sh deploy ARCHIVE EXPECTED_SHA256 [MAX_ROOMS]` или `release.sh rollback BACKUP`. Доступ к ним выдаётся через ограниченный wrapper, который устанавливает второй мастер. Релиз останавливается при занятых комнатах, до остановки блокирует новые входы и сохраняет предыдущий комплект. Результат выпуска и возврата проверяется по точному commit SHA через health/readiness. Сервисный override лимита также восстанавливается.

Первый переход с legacy установки выполняется отдельным планом: прежние версии не имеют manifest и могут завершиться от SIGUSR2. Исторический install.sh не входит в новый артефакт и не является проверенным безопасным способом первичной установки. Сертификаты, Caddy, службы, firewall, журналы, бэкапы и полное удаление установки находятся в ответственности серверного мастера; этот этап их не меняет.

GitHub workflows сейчас проверяют и сохраняют артефакт, но не разворачивают его. Deploy, rollback, production verification и maintenance workflows, ограниченного deployment-пользователя и production approval устанавливает второй мастер после аудита.
